# AAC 插件源码重建可行性

日期：2026-09-22。范围：现有 `ttp_aac.dll` 的伪代码、二进制、接口和已取得的运行结果。
本文保留实施前的分析与建议。后续已建立本 `ttp_aac` 独立工程并完成首版实现；
当前状态、验证与未覆盖分支见 [AAC 插件实现记录](AAC_PLUGIN_IMPLEMENTATION.md)。

## 结论

**可以结合伪代码、机器码、二进制数据和运行对照，重建一个可从源码编译、兼容原接口的
`ttp_aac.dll`，再补充分片 MP4 支持。当前证据足以支持开展这项工作，但尚不足以宣称已经
完整恢复所有行为。**

需要明确“完整”的范围：

| 目标 | 判断 |
| --- | --- |
| 重建插件接口、AAC/MP4 读取、内部 AAC 解码、标签/封面和 Nero 编码适配 | 有明确实现依据，可分模块重建并逐项验证 |
| 新插件运行时不再加载原 `ttp_aac.dll` | 可作为完整替换的验收要求；仅转发原 DLL 不算完成 |
| 继续调用原本就独立存在的 Nero 编码组件 | 与原插件的依赖边界一致，不妨碍重建插件自身 |
| 连 `Aac.dll`、`aacenc32.dll`、`NeroIPP.dll` 的内部编码算法也全部自研恢复 | 仅凭 `ttp_aac.dll` 不够；这些实现位于外部二进制，需要另外分析和验证 |
| 找回原作者逐字相同的 C/C++ 源码、生成逐字节相同的 DLL | 不能从当前材料作此保证；优化后的机器码不唯一对应某份源码 |
| 所有合法/异常输入、所有 AAC 扩展和全部浮点结果都与原版完全相同 | 当前未证明；不能用一个样本成功或反编译函数数量代替验证 |

本次问题的修复目标仍是本地分片 MP4 文件。在线 DASH 清单、分片下载和 DRM 解密属于另外的功能。

## 一、已经取得的重建依据

分析对象：

- x86 `ttp_aac.dll`，314,720 字节。
- SHA-256：`49195708ba9b942edd8215ffcb4e5db73a1548b0c02a5e2b11960ea12af69135`。
- 以下地址均以首选基址 `0x60000000` 表示。
- Ghidra 为识别出的 927 个函数生成了伪代码。这包括运行库和辅助函数，不是 927 个均已人工验证的业务函数。
- PE 中保留了类 RTTI、虚表、导入/导出、资源和静态数据，可用于修正伪代码的类型和布局。
- 静态导入为 `KERNEL32.dll`、`ADVAPI32.dll`、`ole32.dll`、`MSVCR110.dll`。
  Nero 是动态加载的，不能仅凭静态导入表判断没有外部依赖。

### 1.1 四类功能已经定位

`ttpGetSoundAddIn` 位于 `600070D6`。`CAACAddIn` 的枚举函数 `60006A97`
按索引返回四个 creator：

| 索引 | 类 | 主要功能 | 对应入口或虚表 |
| --- | --- | --- | --- |
| 0 | `CMP4ReaderCreator` / `CMP4Reader` | MP4/M4A 格式、采样读取、时长、定位、标签、封面 | reader 虚表 `60029E5C`，Open `60005644`，Read `60005A5B` |
| 1 | `CAACReaderCreator` / `CAACReader` | AAC 文件读取及其附加接口 | reader 虚表 `600297AC`，Open `60001980`，Read `60001DFB` |
| 2 | `CAACDecoderCreator` / `CAACDecoder` | 压缩 AAC 包解码为 PCM | 虚表 `6002A054`，初始化 `60006604`，输出 `60006D71` |
| 3 | `CM4AEncoderCreator` / `CM4AEncoder` | Nero 编码配置、输入转换、写入和结束 | encoder 虚表 `60029C84`，Open `60003709` |

插件初始化 `600070F6` 还查找宿主的 `CreateStdContent`、`GetSoundCodecName`、
`CreateStreamOnFile`。源码恢复需要遵守这些宿主接口、GUID、调用约定、内存释放方式和引用计数。

主虚表之外，MP4 reader 还有 metadata、thumbnail 和其它附加接口；AAC reader 没有同样的
thumbnail 能力。恢复播放成功不能代替文件属性、写标签和封面保存的恢复。

### 1.2 解码核心包含在插件内部

已定位的调用链：

```text
CAACDecoder::初始化（60006604）
  → 创建解码状态（60007890）
  → 解析 AudioSpecificConfig（600076E0）
  → 取得/设置输出配置（60007420 / 600079C0）

CAACDecoder::输出（60006D71）
  → 带调用方输出缓冲的解码入口（600073E0）
  → 帧解码（60007A30）

定位后重置（60006A53）
  → 解码状态重置（600079A0）
```

这条播放解码路径进入本 DLL 内部实现。前一轮已在宿主和 Win7 用原插件完整解码普通 MP4
对照文件，因此“必须依赖新版 Windows AAC 解码器才能重建播放”没有依据。
新插件的 XP/Win7 可运行性仍需另行编译、检查导入并实机验证。

### 1.3 FAAD2 来源的证据与尚未确认之处

本轮读取了二进制 `600463C0` 的错误字符串指针表，并与上游 `FAAD2_2_7` 对照：
**34 条错误文字及其顺序全部相同**。解码状态的创建、销毁、配置、带外部缓冲解码和定位后重置
也有对应结构。来源：上游 [error.c](https://github.com/knik0/faad2/blob/FAAD2_2_7/libfaad/error.c)
与 [decoder.c](https://github.com/knik0/faad2/blob/FAAD2_2_7/libfaad/decoder.c)。

MP4 的类型分派、按 `stts` 求采样数等结构也与旧 `mp4ff` 有对应关系。
参考上游 [mp4ff.c](https://github.com/knik0/faad2/blob/FAAD2_2_7/common/mp4ff/mp4ff.c)
和 [mp4atom.c](https://github.com/knik0/faad2/blob/FAAD2_2_7/common/mp4ff/mp4atom.c)。

因此可以高置信度判断属于 FAAD2 / 旧 mp4ff 代码家族；**不能据此锁定它恰好等于未经修改的
FAAD2 2.7，也不能把上游支持的所有功能直接视为该 DLL 已启用的功能。**

已经发现的差异包括：

1. 插件的 `600076E0` 接收第六个参数，用于返回输出帧长；上游该版 `NeAACDecInit2`
   是五参数接口。机器码 `60006698` 至 `600066A3` 六次压栈，调用后 `ADD ESP,0x18`，
   证实这不是仅由反编译参数猜测得到的结论。该结果参与输出缓冲大小计算。
2. 插件 `60023346` 每次将 `stts` 表指针增加 8 字节读取下一个 sample count，
   即 count/delta 成对存储；对照的上游版本使用两个独立数组。
3. 插件的 MP4 类型编号中存在额外位置，例如 `stz2` 对应 `0x8E`，后续编号与该上游版本不同。
   识别出类型编号本身也不代表该类型已完整实现。

上游源码可帮助命名与核对算法，插件二进制仍是原版差异的判断依据。
若实施时复用上游源码，应保留其许可及来源说明；本轮仅将对照材料放在本地测试目录。

## 二、为什么“伪代码 + 二进制”比只看伪代码更可行

### 2.1 可以补回伪代码没有表达完整的信息

- **数据表**：从 PE 节及引用关系恢复 Huffman、窗函数、滤波和数值常量等数据；确认数组边界、
  元素类型、字节序和浮点位模式。`DAT_...` 名字并不包含数据本身。
- **参数与返回值**：从调用方压栈、寄存器使用及返回指令核对 `cdecl/stdcall/thiscall`、
  `HRESULT`、字节返回值和隐藏对象指针。
- **对象布局**：结合构造/析构、RTTI、QI 和虚表确认多接口对象偏移及所有权。
- **控制流**：汇编用于还原间接调用、跳转表、异常清理和内联后的流程。
- **资源与协议常量**：恢复 GUID、字符串、能力标记和错误码，使现有宿主按原接口工作。

具体例子：`600076E0` 的伪代码被输出成 `void`，但调用方在返回后执行 `TEST AL,AL` 和负值分支；
重建时必须恢复真实返回语义，不能照抄 `void`。

当前伪代码包含 208 处工具警告，其中许多是异常处理替换、运行库或导入跳板。
这个数字既不代表 208 个业务缺陷，也不能被忽略后直接把输出当可编译源码。

### 2.2 还必须用原 DLL 做运行对照

静态材料不能独自证明所有路径正确，尤其包括：

- 第一包预热、首尾采样处理、空输出与 EOF 的区别。
- SBR/PS 的采样率和声道变化、AAC 不同配置的实际启用范围。
- seek 后重置、输出缓冲容量和连续多次读取。
- 浮点算法的运算顺序、x87/SSE 和舍入差异。
- 多 reader/decoder 同时存在时的共享状态和生命周期。
- 修改标签、封面后对原音频数据及未知 box 的保留。

原 DLL 可以作为行为对照工具，不应成为新插件正常运行时的隐藏转发依赖。
PCM 一致性需区分“逐样本位一致”和“经量化、舍入说明后的数值一致”，不能只听起来正常就判定完成。

## 三、Nero 编码边界

`60003CC7` 动态加载 `Aac.dll`，取得 `NERO_PLUGIN_GetPrimaryAudioObject`。
编码配置 `600035FB`、编码 Open `60003709` 等随后调用外部对象。
已有转换恢复记录进一步确认其 `aacenc32.dll`、`NeroIPP.dll` 依赖，见
[播放器转换恢复记录](../../rebuild/docs/CONVERSION_RECOVERY.md)（本地相邻 rebuild 工程）。

因此需要分别描述：

1. **重建 `CM4AEncoder` 适配层**：恢复格式检查、PCM 转换、外部接口、配置调用、标签传递、
   最终写入和错误返回。保留同一组外部 Nero 组件时，有条件恢复原编码功能。
2. **重建 Nero 编码算法及其界面实现**：这不是本 DLL 内的完整代码。
   若也要求摆脱这组依赖，需要扩展分析对象；换一个 AAC 编码库也不能称为 Nero 输出原样恢复。

例如输入采样率超过 48 kHz 时返回 `0x8BDA0602`，在 `60003709` 中有明确分支。
这种可观察行为应在原功能对照中保留记录；日后扩展支持应另行说明。

## 四、建议实施顺序

### 阶段 1：接口和数据恢复

建立函数地址到源码职责的映射，恢复四种 creator、GUID、虚表语义、资源、内存所有权、
错误码及动态依赖。整理内部解码器的类型、编译配置和常量表，特别核对上述原版改动。

产物是可以编译和加载的独立插件工程；未实现的能力不能提前标记为完整支持。

### 阶段 2：恢复原有播放与属性功能

按依赖恢复 AAC reader、普通 MP4 reader、AAC decoder，以及定位、格式查询、
标签和封面读写。恢复 Nero 适配层，完成全部原功能的对照后，才称为原插件功能重建。

对普通 MP4 验证时，保留 reader 向 decoder 交付压缩包的分层，避免把系统 Media Foundation
能否读取容器混入插件本身的验收。

### 阶段 3：在容器层增加分片 MP4

推荐建立统一的采样描述：音轨、64 位文件位置、包大小、解码时间、时长、必要的呈现时间信息。
传统采样表和分片结构各自生成该索引，共用后续读取/定位与原 AAC 解码核心。

至少补充：

- `mvex/trex` 的轨道默认值。
- `moof/traf/tfhd/trun` 的轨道归属、字段覆盖规则、sample size/duration 和数据位置计算。
- `tfdt`、连续分片的解码时间和缺失字段时的合法推导。
- 多个 `traf/trun/mdat`、64 位 box 长度和偏移、截断与越界检查。
- 从有效采样时间建立时长和 seek；`sidx` 可辅助定位，但不能取代逐包索引。
- 音轨选择、edit list/首尾裁剪及不支持的配置或加密的明确错误。

**这不是在类型分类器加几个 case 就能完成。** 当前旧 reader 的 sample count、Read 和 seek
都依赖传统采样表。新增分片索引后，这些消费索引的路径也必须一起接通。

分片文件的标签/封面读取可以随容器解析支持；写入须单独验证。
在正确处理 box 移动及其相关偏移前，不应把传统 MP4 写标签逻辑直接用于分片文件。

### 阶段 4：系统与回归验收后替换发行插件

先在隔离目录加载新插件，避免新旧同类 creator 的优先级使测试仍然调用旧实现。
确认新插件不加载原 `ttp_aac.dll` 后，再替换两种发行包中的插件。

普通版和 XP/Win7 版均使用可控的插件容器/解码路径。旧系统版需要对新 DLL 及依赖做静态导入检查，
并在 XP、Win7 内验证；不能仅以现代宿主机成功作为兼容结论。

测试代码及样本继续放在 `rebuild/tests`，不上传测试代码，Actions 不运行本地测试。

## 五、完成标准

| 类别 | 验证内容 |
| --- | --- |
| ABI | 四个 creator、接口查询、引用计数、缓冲释放、返回码、宿主导出调用 |
| 原解码功能 | AAC 文件及普通 MP4/M4A；按确认过的配置建立 LC、HE-AAC/SBR、PS、多声道等样本矩阵，未验证项明确列出 |
| 状态与时间 | 连续播放、EOF、空包、重复 seek、首尾、短文件、并发读取、首尾采样与时长 |
| 文件属性 | 读取/写回标签，封面添加/替换/移除，重新打开，音频压缩包保持一致 |
| 编码 | Nero 配置、取消、实际编码、Finalize、错误返回和组件缺失 |
| 新分片支持 | 本次 Bilibili 样本、不同分片默认值/偏移组织、多音轨、定位和截断文件 |
| 系统 | XP/Win7 及普通版目标 Windows 上加载与实际解码；导入检查和资源释放 |

本次 Bilibili 样本有 52 个分片、10,995 个 AAC 包。
前一轮流复制成普通 MP4 后，全部压缩包内容与顺序一致，原插件能完整解码。
这证明问题集中在分片容器读取，为阶段 3 提供了可重复的验收样本；
它尚不证明所有 AAC 格式已经覆盖。详见 [分片 MP4 分析](FRAGMENTED_MP4_AAC_ANALYSIS.md)。
